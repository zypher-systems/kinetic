# 0.2.0 testing

Testing of ZypherOS Kinetic 0.2.0 ("Daily driver"; scope in [decisions](decisions.md#020-daily-driver-locked)). First in the VM (`scripts/vm.sh`: UEFI, Secure Boot, 8 GB RAM), then on a Lenovo ThinkPad Z16.

## Upgrade from 0.1.0 (VM, 2026-09-27)

The VM disk from the third 0.1.0 install was upgraded with `sudo dnf upgrade 'kinetic-*' 'zypheros-*'` from a local copy of the 0.2.0 packages, as an installed system would from the published repository.

| Check | Result |
| --- | --- |
| Upgrade transaction | Clean. `desktop-backgrounds-kde` replaced automatically, `jetbrains-mono-fonts` pulled in, pre/post snapshots taken |
| `os-release` | `ZypherOS Kinetic 0.2.0` |
| Firewall | Default zone switched to `ZypherOSKinetic` at once, without a reboot; the network interface moved into it |
| Docker | Ports published on `127.0.0.1`, including a container created under 0.1.0 with `-p 8080:80` once it restarted. `localhost` works; the VM's network address is refused |
| Shortcuts | Applied to the existing 0.1.0 account at its next login: Meta+Return opens Ghostty, Meta+B Chromium (the power profile no longer changes), Meta+Space search |
| Monospace font | JetBrains Mono for KDE apps and for everything that asks fontconfig for "monospace" |
| Wallpaper | Plasma's `Default` wallpaper is the Kinetic one |

## Rollback (VM)

| Test | Result |
| --- | --- |
| `snapper undochange` on the upgrade's pre/post pair | **Not reliable for updates:** files went back to 0.1.0, but rpm still listed the 0.2.0 packages. rpm's SQLite database was written to disk after the post snapshot. [recovery.md](recovery.md) says not to use it for updates |
| Btrfs Assistant restore of the pre-upgrade snapshot | Clean 0.1.0 system: packages and files agree (`rpm --verify` clean), snapshot history intact, the Docker volume's data intact, `/home` untouched. Btrfs Assistant moved the nested subvolumes (`.snapshots`, Docker, Podman, libvirt, machines) into the restored root |
| Upgrade again after the rollback | Clean |
| Restore across a kernel update (a kernel installed, then its pre snapshot restored) | **Failed before the fix:** the boot menu's default was still the removed kernel, which dropped into emergency mode (no drivers, so `/boot/efi` couldn't mount), with the root account locked. After the fix, `kinetic-boot-repair` switched the default, removed the stale entry, and restarted: working desktop after one extra reboot, no input needed |
| Previous kernel from the GRUB menu | Works. The menu shows by itself after a failed boot (5 second countdown); tapping Esc shows it otherwise |
| Updates from Discover | Snapshotted too (PackageKit uses dnf5), now labelled "Discover (PackageKit)" |
| Deleting `root_backup_*` after a restore | Works with the commands in recovery.md |

## Bugs found and fixed

| Problem | Cause | Fix |
| --- | --- | --- |
| Docker doesn't start from the second boot on (0.1.0) | `kinetic-snapshots-setup.service` was ordered before `docker.socket`, but as a normal service it also runs after `basic.target`, which waits for all sockets. systemd broke the cycle by dropping a job, not always the same one. The third 0.1.0 install passed because it was never rebooted | Ordered before the Docker, containerd, Podman, and libvirt services instead of their sockets |
| Restoring a snapshot from before a kernel update leaves the machine unbootable by default | `/boot` isn't part of snapshots, so GRUB still defaults to the kernel the restore removed | `kinetic-boot-repair.service` in `kinetic-snapshots` |
| Chromium's first run opens Fedora's start page and an empty "Additional Terms of Service" dialog | Fedora's `master_preferences`, and a placeholder dialog in Fedora's Chromium 154 | Chromium's first run is marked done for accounts that haven't used Chromium yet |
| Plasma Setup's background is Fedora's F44 wallpaper (0.1.0), then blank (first 0.2.0 ISO) | Fedora's Plasma Setup loads two fixed files from the `Default` wallpaper: `5120x2880.jxl` (or `1440x2960.jxl` in portrait), from `images_dark/` with the dark theme | `kinetic-backgrounds` provides `system-backgrounds-kde`, points `Default` at the Kinetic wallpaper, and ships those JPEG XL files |
| `vm.sh start` booted the installed disk instead of the ISO | UEFI prefers the installed system's saved boot entry over QEMU's `-boot order` | The ISO drive gets `bootindex=0` |
| `opencode` installed the old OpenCode v1 (found on the reference desktop); switching to the v2 installer then hung on first run | OpenCode moved its installer to `opencode.ai/v2/install`. The v2 installer checks for an existing install by running `opencode --version`, which found Kinetic's launcher, itself waiting on the first-run lock | The launcher uses the v2 installer; vendor installers run without Kinetic's launchers on their PATH, and a launcher started during an install exits instead of waiting. Verified in a clean Fedora 44 container, and in the live session of the ISO of 2026-09-30: the first run installs OpenCode 2.0.20 in about 20 seconds and starts it |
| Snapshots of Discover updates are labelled `/usr/libexec/packagekitd` | The snapshot description is the command that started the transaction | Labelled "Discover (PackageKit)" |

## Fresh encrypted install (VM, ISO of 2026-09-27 18:09)

Installed with **Encrypt my data** under Secure Boot, with an emulated TPM (`vm.sh start --tpm`).

| Check | Result |
| --- | --- |
| Encryption | LUKS2 (aes-xts) for `/` and `/home`; `/boot` and EFI unencrypted. The branded boot splash asks for the passphrase |
| Plasma Setup | Creates the user in `wheel`, `docker`, and `libvirt`. Background was blank in this ISO (fixed, below); with the fixed package it shows the Kinetic wallpaper |
| Defaults from the start | `ZypherOSKinetic` firewall zone, Docker on `127.0.0.1`, JetBrains Mono, shortcuts for the new account (Meta+Return opened Ghostty in its first session), Chromium's first run skipped, boot menu repair present and idle |
| First boot | Snapper baseline and pre/post snapshots, the Docker, Podman, libvirt, and machines subvolumes, Cursor, Grok Bot, Flatseal, and Gear Lever |
| TPM unlock | `systemd-cryptenroll` with PCR 7, `tpm2-device=auto` in crypttab, `dracut -f`: boots without the passphrase. With `--tpm2-with-pin=yes` the splash asks for the PIN instead, and it boots. A recovery key enrolls alongside. The VM's firmware (Fedora's 2 MB OVMF build) doesn't measure the boot, so PCR 7 isn't enforced there; that part is for the Z16 |
| Restore from the live USB | Unlocked the disk in Dolphin, restored a pre snapshot in Btrfs Assistant (Snapper → Browse/Restore), booted the installed system: the change was undone, snapshot history and container subvolumes intact |

## Lenovo ThinkPad Z16, first attempts (2026-09-28)

Booted from a Ventoy stick ("Boot in grub2 mode"), over an existing LUKS-encrypted Linux install.

- The live session runs.
- The installer took 3–4 minutes on "Initializing…" before it appeared. Launching it again while the first instance was still starting failed, since only one installer can run at a time.
- The install then failed with "error initializing rsync", while copying the system to the disk, and Anaconda's crash reporter asked for a Red Hat Bugzilla API key.

Not reproduced in the VM: from a real Ventoy 1.1.17 stick (exFAT, grub2 mode), with or without an existing LUKS install or a network, the installer appears in about 15 seconds and a full encrypted install completes. The ISO's checksum on the Ventoy drive (a 2 TB SanDisk Extreme SSD) matched.

**Installed cleanly** from the same ISO written directly to a USB drive: the installer started quickly and the install completed. The failure is specific to booting through Ventoy from that SSD; Fedora 44's own ISO installs from it, so a likely cause is how Ventoy maps a large ISO file on that drive, which Ventoy's own checksum doesn't exercise. Unconfirmed. If an install from Ventoy fails, write the ISO directly to a drive.
